# Решения по неоднозначностям ТЗ

Документ фиксирует выбор в спорных местах, чтобы не останавливаться на уточнениях. Дополняется по ходу разработки.

## Пивот со старого scaffold

В репозитории на момент старта лежал каркас другого проекта — лендинг с админкой на пароле, Supabase и Resend (`middleware.ts`, `.env.example` с ключами Supabase/Resend, `package.json` с `@supabase/supabase-js`/`resend`). Он не имеет отношения к платформе организаторов из ТЗ (Next.js + Prisma/PostgreSQL + Telegram Login + grammY + node-cron). Каркас заменён полностью. Ветвевые файлы с брендингом (`Губкин Design System.docx`, логотип, фото) сохранены и перенесены в `brand/` — они не мешают и могут пригодиться для визуального стиля.

## Прочее

- **Аутентификация без Edge middleware.** Подпись сессии и хэши паролей используют `node:crypto`, который недоступен в Edge Runtime. Поэтому проверка прав вынесена в серверные компоненты/server actions (`lib/auth.ts`), а не в `middleware.ts`. Это проще и не требует Edge-совместимых JWT-библиотек.
- **Сессия.** Простой подписанный cookie (HMAC над JSON-пейлоадом `{userId, exp}`), без внешних auth-фреймворков — их функциональность избыточна для одного способа входа.
- **Хранение времени.** Все `DateTime` в Postgres — `timestamptz` (UTC), Prisma это делает по умолчанию для `DateTime`. Форматирование в МСК — на уровне отображения (`lib/time.ts`, `Intl.DateTimeFormat` с `timeZone: 'Europe/Moscow'`).
- **`targetDate`/день мероприятия.** Хранится как `DateTime` (полночь UTC даты), фактическое время — в свободном поле `timeSlot`. Задачи группы `EVENT_DAY` получают `dueDate = targetDate` (сравнение по дате, не по времени).
- **Автоназначение при отсутствии человека в отделе.** Задача создаётся с `assigneeId = null`, в интерфейсе подсвечивается как «без исполнителя» (класс/бейдж), это и есть требуемая подсветка — отдельного поля не заводим.
- **Триггер `SECURITY_SUBMITTED`.** Добавлен в enum `EventTrigger` вместе с `DATE_FIXED`, `SECURITY_ANSWERED`, `REGISTRATION_CLOSED`, `EVENT_DONE`, как указано в разделе 7.
- **Тесты.** Vitest, без БД — тестируется чистая логика генерации дат/исполнителей и функции проверки условий перехода стадий (принимают на вход простые объекты, не Prisma-клиент), чтобы не требовать поднятой Postgres в CI.
- **Cron.** `node-cron` внутри Next.js процесса, запуск планировщика через `instrumentation.ts` (официальный хук Next.js для кода, который должен выполниться один раз при старте сервера), с флагом в module-scope против повторной регистрации при hot-reload.
- **Бот и веб — один процесс.** grammY-бот запускается тем же `instrumentation.ts` через long polling; вебхук не настраиваем, чтобы не требовать публичного HTTPS для дев-окружения.
- **Идеи и авторство.** Для анонимной идеи `authorId` не просто `null`, а действительно не передаётся в `create()` — Prisma подставит `null` как дефолт колонки, поле никогда не заполняется значением текущего пользователя, даже если он вошёл.
- **Доска/список/календарь** — один серверный маршрут `/`, вид и фильтры живут в query-параметрах (`?view=…&type=…`), без клиентского состояния: ссылки шарятся, работает без JS, открывается из Телеграма сразу в нужном виде.
- **Markdown.** Рендерится библиотекой `marked` (маленькая, без рантайм-зависимостей). Контент markdown (регламенты, описание мероприятия) редактируют только LEAD/ADMIN — это доверенные внутренние пользователи, поэтому HTML не прогоняется через дополнительный санитайзер (как и в обычных wiki-инструментах для закрытой команды).

## После аудита (сценарии ролей в браузере)

- **Тёмная тема.** Светлый интерфейс из раздела 10 заменён на тёмно-синий со свечением по прямому запросу пользователя (присланы два референса). Токены остались семантическими (`bg/surface/ink/muted/line/gold`), так что переключение обратно — правка `tailwind.config.ts`.
- **Предварительная дата.** В `PLANNING` дату можно сохранить как предварительную (`dateFixed = false`) — она видна в календаре и списке, но план не разворачивается. Отдельная кнопка «Зафиксировать дату» переводит в `IN_PROGRESS` и генерирует задачи. Это использует уже заложенную в модель пару `targetDate`/`dateFixed`.
- **Автозакрытие задач.** Добавлено поле `TaskTemplate.autoComplete` (`PHOTO_REPORT_ATTACHED`, `RETRO_SAVED`): задачи «Ссылка на фотоотчёт прикреплена» и «Ретро заполнено, посещаемость внесена» закрываются по факту появления данных в карточке, а не галочкой — прямое следствие принципа 1 ТЗ. Настраивается в `/settings`.
- **Guards стадий.** Каждое действие перехода проверяет, что мероприятие находится в ожидаемой стадии, — иначе устаревшая вкладка или двойной клик могли бы, например, согласовать уже закрытое мероприятие.
- **Уведомление лиду о решении** (согласовано/возвращено/отклонено) — не требовалось ТЗ явно, но это тот же принцип push: лиду не нужно заходить проверять статус.
- **Стоп-лист** не только шлёт уведомление, но и кладёт список незакрытых обязательных задач в описание задачи «Стоп-лист» (создаёт её, если шаблон без неё).
- **Удаление мероприятия** — только ADMIN, с подтверждением в карточке; идея, из которой оно создано, отвязывается.
- **Поиск в шапке** ведёт в список мероприятий с фильтром по названию; глобальный поиск по людям/тегам не реализован (вне объёма первой версии).

## Аудит-2

- **Московские сутки.** «Сегодня» для просрочек, календаря, стоп-листа и «проведено не раньше даты» считается по Москве (`calendarDay` в `lib/time.ts`), а не по UTC — иначе с 00:00 до 03:00 МСК задачи на сегодня считались бы ещё не наступившими, а вчерашние — не просроченными. Даты по-прежнему хранятся полуночью UTC.
- **«Зафиксировать дату с гостем»** закрывается сама при фиксации даты (`autoComplete = DATE_FIXED`): план разворачивается только фиксацией, значит, дата уже есть — ставить галочку второй раз незачем.
- **Уведомления не теряются.** В `NotificationLog` пишется только доставленное; просрочка помечается «уведомлённой», только если сообщение ушло или упёрлось в лимит «тишины» (тогда оно в дайджесте). Если бот ещё не настроен, всё уйдёт при следующем тике после подключения.
- **Создание мероприятия**: сразу выбирается лид (по умолчанию — создатель) и можно отправить на согласование одной кнопкой; для этого описание обязательно — то же условие входа в `APPROVAL`, что и в карточке.
- **Смена лида** переводит на нового лида его открытые задачи «без отдела» (личные приглашения, стоп-лист, ретро) — иначе они остались бы на прежнем человеке.
- **Отклонённое** администратор может вернуть в «Идеи» с комментарием — отклонение не навсегда.
- **Регламенты**: новый регламент создаёт только ADMIN; редактируют LEAD и ADMIN, как в разделе 4. Сохранение без изменений не плодит пустых версий.
- **Идеи**: голосовать можно только после входа (иначе голос не к кому привязать) — у гостя кнопка ведёт на вход. ADMIN может удалить идею.

## Подготовка к запуску (вход, кабинет, демо-данные)

- **Вход по человеку и паролю роли вместо Telegram Login.** Отступление от ТЗ по прямому запросу заказчика: Telegram-виджет требовал настроенного домена у @BotFather и не работал у людей. Теперь человек выбирает себя в списке и вводит общий пароль своей роли (Участник / Руководитель / Администратор). Пароли хранятся в таблице `AppSetting` как scrypt-хэши, по умолчанию `member-gubkin` / `lead-gubkin` / `admin-gubkin` (или из `MEMBER_PASSWORD`/`LEAD_PASSWORD`/`ADMIN_PASSWORD` при первом запуске), меняются в «Настройки → Доступ и запуск»; пока пароль стандартный, админ видит предупреждение. Компромисс осознанный: внутри роли человек технически может войти за коллегу — для закрытой команды клуба это приемлемо, а в «Истории» видно, кто что делал. Роль «Читатель» не входит — это просто гость без входа.
- **Telegram — только для уведомлений.** Привязка через профиль: кнопка открывает бота с подписанной ссылкой `/start <userId>_<HMAC>`, бот записывает `telegramId` человеку. Без привязки уведомление получает результат `no_bot` и не теряется (журнал пишется только при доставке). `ADMIN_TELEGRAM_IDS` больше не нужен: первый администратор создаётся сидом, дальше роли раздаются в «Настройки → Люди».
- **Демо-данные помечены флагом `isDemo`** (люди, мероприятие, идеи) и сеются один раз (флаг `demo_seeded`), поэтому повторный сид при каждом деплое на Render не возвращает удалённое. Удаление — кнопкой в настройках; всё, что демо-люди успели сделать в настоящих мероприятиях, переходит к удаляющему администратору, задачи — без исполнителя. Удалять из-под демо-аккаунта запрещено, чтобы админ не выкинул сам себя.
- **«Мой день» как личный кабинет.** По ТЗ — задачи и мероприятия человека. Добавлено то, что человек иначе ищет сам: регламент своего отдела и общие регламенты; группировка задач по срокам (просрочено / сегодня / неделя / позже / ждут события с подписью, какого); блок «Требует вашего решения» (отправить на согласование, зафиксировать дату, заполнить итоги, согласовать, застрявшие); для руководителя и заместителя отдела — задачи отдела без исполнителя с кнопкой «Взять на себя» и загрузка команды. Задачу можно закрыть прямо из кабинета.
- **Идея → мероприятие теперь может и руководитель**, а не только админ: создавать мероприятия руководителям разрешено разделом 4, а идея — просто быстрый способ это сделать. Руководитель становится лидом созданного мероприятия.
- **Отзывчивость на медленном хостинге.** Полоса загрузки при переходах, «занятая» кнопка при отправке форм, скелетоны `loading.tsx`, и `staleTimes.dynamic = 0`, чтобы после действия Поток не показывал копию из клиентского кэша. Причина жалобы «Поток не нажимается» — засыпающий бесплатный инстанс Render: клик срабатывал, но ответ шёл до минуты без какой-либо реакции интерфейса.
