# Бизнес-клуб Губкина — CRM организаторов

Простая CRM для подготовки мероприятий клуба по регламенту v3. Разделы:

- **Мероприятия** — доска по этапам и список; карточка мероприятия одной
  страницей: что сейчас нужно сделать, готовое сообщение для рабочего чата,
  задачи по ролям, итоги.
- **Мои задачи** — задачи вашей роли: просрочено, сегодня, на неделе, позже,
  ждут другого шага; и ваш шаг по мероприятиям.
- **Регламент** — общая схема, задачи каждой роли со сроками и описанием,
  общие правила. Есть кнопка «Распечатать».
- **Настройки** (только Администратор клуба) — роли и теги для чата, пароли,
  шаблоны задач, обслуживание.

Напоминания — в Telegram. Решения по неоднозначностям — в
[`DECISIONS.md`](./DECISIONS.md). Скриншоты — в [`docs/screens`](./docs/screens).

Стек: Next.js (App Router) + TypeScript + Tailwind, PostgreSQL + Prisma,
grammY-бот, node-cron.

## Вход по ролям

В CRM нет личных аккаунтов — только пять ролей:

| Роль | Чем занимается | Вход |
|---|---|---|
| Администратор клуба | руководство: даты, проверка регистраций, итоги, настройки | по паролю |
| Внешний отдел | находит спикеров и ведёт их | одним нажатием |
| Пиар и пропуска | посты и анонсы, пропуск на спикера, бронь аудитории | одним нажатием |
| Event-отдел | план проведения, площадка, техника, люди | одним нажатием |
| Контент | рилсы, съёмка, фото | одним нажатием |

- На странице входа можно указать, как подписать вас в истории (например,
  имя). Подпись запоминается на устройстве, в истории видно «Роль · имя».
- Сменить роль — меню аватара справа вверху → «Сменить роль».
- В «Настройки → Доступ» можно включить **общий пароль для отделов**
  (по умолчанию выключен).
- Сайт закрыт от поисковиков (`noindex`), без входа видна только страница входа.

### Пароль администратора

Пароля по умолчанию нет — репозиторий публичный. Пароль задаётся переменной
окружения `ADMIN_PASSWORD` на сервере (на Render: сервис → Environment).
После первого входа его можно сменить в «Настройки → Доступ». В базе хранится
только scrypt-хэш. Пароль может быть по-русски и с пробелами.

Пока пароль не задан нигде, на карточке администратора написано
«Пароль администратора не задан. Укажите ADMIN_PASSWORD в настройках сервера».

### Кто что может

| Действие | Кто |
|---|---|
| Смотреть всё | все роли |
| Создать мероприятие | Администратор, Внешний отдел |
| Вносить варианты дат | Администратор, Пиар |
| «Спикер подтвердил» (фиксация даты) | Администратор, Внешний отдел |
| «Пропуск не одобрен» | Администратор, Пиар |
| Закрывать задачи | своя роль (Администратор — любые) |
| «Проведено», итоги, закрыть | Администратор, Внешний отдел |
| Отменить, удалить | Администратор |
| Настройки | Администратор |

Права проверяются на сервере, кнопки показываются по тем же правилам.

## Как идёт мероприятие (регламент v3)

Этапы: **Черновик → Подбор дат → Дата у спикера → Подготовка → Проведено →
Закрыто**, отдельно **Отменено**.

1. **Внешний отдел** заводит карточку, когда спикер одобрил двухнедельное
   окно: «Мероприятия» → «Новое мероприятие». ФИО, род деятельности,
   компания, о чём, формат, направление, окно спикера. Если всё заполнено,
   мероприятие сразу уходит в «Подбор дат», иначе остаётся черновиком.
2. **Пиар или Администратор** вносят 3–4 варианта: дата, время (15:45 /
   17:15 / 17:20 или своё), аудитория → «Варианты готовы».
3. **Внешний отдел** согласует со спикером один вариант, отмечает
   «Предупредил спикера, что пропуск могут не одобрить» → «Спикер подтвердил».
   Разворачивается план задач. Если до мероприятия меньше 12 дней, CRM
   предупредит «Не успеем по регламенту» и попросит подтвердить.
4. **Пиар** оформляет пропуск и закрывает задачу «Оформить пропуск на
   спикера» — это «Пропуск готов»: Event-отдел и Контент получают задачи.
   Если пропуск не одобрили — «Пропуск не одобрен» с причиной: мероприятие
   отменяется, Внешний отдел и Администратор получают «Сообщите спикеру».
5. **День мероприятия** — «Тайминг дня» (`/events/<id>/day`): шаги по
   порядку со временем от начала, каждый отмечает свои с телефона.
6. «Проведено» → задачи «после» → фотоотчёт, посещаемость, ретро → «Закрыть».

На ключевых шагах (карточка создана, дата зафиксирована, пропуск готов)
в карточке появляется готовый текст для рабочего чата с кнопкой
«Скопировать». Кого тегать — «Настройки → Роли».

Направления: «Лекция / питч-сессия», «Бизнес-кейс», «Интенсив» (цикл и
номер встречи), «Акселератор». Для кейса и акселератора шаблон базовый —
руководство уточнит.

## Как добавить мероприятие

Войдите как «Внешний отдел» (или Администратор) → «Мероприятия» →
«Новое мероприятие» → заполните карточку спикера → «Сохранить карточку».

## Render: обновление и база данных

Сервис разворачивается по `render.yaml` из ветки
`claude/business-club-platform-y0k1oq`. Новые изменения: сервис `gubkin-bc`
→ **Manual Deploy** → **Deploy latest commit**. При запуске применяются
миграции и сид.

После обновления до v3 обязательно задайте `ADMIN_PASSWORD` в Environment
сервиса — старые пароли по умолчанию больше не работают.

> **Внимание: бесплатная PostgreSQL на Render истекает через 30 дней после
> создания.** После этого есть 14 дней, чтобы перейти на платный план,
> иначе база удаляется вместе со всеми данными. Проверьте дату создания
> базы `gubkin-db` в панели Render.

Варианты:

- **Перейти на платный план базы** в панели Render (база → Upgrade).
  Данные сохранятся.
- **Перенести на другую PostgreSQL** (любой провайдер):
  1. Создайте новую базу и возьмите её строку подключения
     (`postgresql://user:password@host:5432/db`).
  2. Перенесите данные: `pg_dump "<старый External Database URL>" -Fc -f crm.dump`,
     затем `pg_restore --no-owner -d "<новая строка>" crm.dump`.
  3. В сервисе `gubkin-bc` → Environment замените `DATABASE_URL` на новую
     строку и перезапустите. Если значение вернётся при синхронизации
     Blueprint, поправьте `render.yaml` вручную.

План в `render.yaml` не меняется автоматически — решение за руководством.

Бесплатный веб-сервис засыпает после 15 минут простоя, первое открытие
может занять до минуты.

## Быстрый старт (Docker)

```bash
cp .env.example .env
# впишите SESSION_SECRET и ADMIN_PASSWORD; для уведомлений — TELEGRAM_BOT_TOKEN, TELEGRAM_BOT_USERNAME
docker compose up --build
```

Приложение — `http://localhost:3000`, миграции и сид выполняются при старте.

## Локальный запуск без Docker

Нужен Node.js 20+ и PostgreSQL 16.

```bash
npm install
cp .env.example .env   # укажите DATABASE_URL и ADMIN_PASSWORD
npm run db:migrate
npm run db:seed        # роли, шаблоны v3, общие правила; безопасно запускать повторно
npm run dev
```

Сид однократно (флаг `regulation:v3`) переводит старую базу на v3: удаляет
демо-данные, создаёт пять ролей, отключает личные аккаунты (история
сохраняется и переходит к ролям), заменяет шаблоны задач. Настоящие
мероприятия не удаляются. Удалить все мероприятия можно в
«Настройки → Обслуживание» (подтверждение словом УДАЛИТЬ).

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | строка подключения к Postgres |
| `SESSION_SECRET` | секрет для подписи cookie (любая случайная строка) |
| `ADMIN_PASSWORD` | пароль Администратора клуба (значение задаёте сами, в репозитории его нет) |
| `TELEGRAM_BOT_TOKEN` | токен бота от @BotFather |
| `TELEGRAM_BOT_USERNAME` | имя бота без `@` |
| `APP_URL` | публичный адрес для ссылок в уведомлениях |
| `TZ` | `Europe/Moscow` |
| `ENABLE_SCHEDULER` | `true` — поднять cron и бота в этом процессе (только на одном инстансе) |
| `TELEGRAM_DRY_RUN` | `1` — печатать уведомления в консоль вместо отправки |

## Уведомления в Telegram

1. В @BotFather: `/newbot` → username в `TELEGRAM_BOT_USERNAME`, токен в
   `TELEGRAM_BOT_TOKEN`, перезапустить приложение.
2. Каждый участник входит в свою роль → аватар → «Профиль и Telegram» →
   «Подключить Telegram». У одной роли может быть несколько подписчиков,
   там же видно, сколько подключено, и можно отключиться.
3. Не больше 3 сообщений в день на подписчика, без повторов; остальное — в
   утреннем дайджесте (09:00 МСК).

Кому что приходит: карточка создана → Администратор и Пиар; варианты дат
готовы → Внешний отдел; дата зафиксирована → Пиар; пропуск готов → Event-отдел
и Контент; пропуск не одобрен → Внешний отдел и Администратор.

Ручной запуск проверки уведомлений (под Администратором):
`POST /api/cron/run?digest=1`.

## Шаблоны задач

«Настройки → Шаблоны»: срок, роль, триггер, описание «как сделать», тайминг
дня мероприятия. Правка действует на новые планы. Шаблон по умолчанию —
`lib/tasks/lecture-template.ts`; если правите файл, увеличьте
`LECTURE_TEMPLATE_VERSION` — сид заменит шаблоны в базе.

## Тесты

```bash
npm run test
```

Юнит-тесты без базы: матрица прав, пароли (кириллица с пробелами),
переходы этапов и предупреждения по срокам, шаблон v3 и «Пропуск готов»,
генерация плана, тайминг дня, сообщения для чата, уведомления.

## Структура

- `prisma/schema.prisma`, `prisma/migrations/` — модель данных.
- `prisma/seed.ts` — сид и переход на v3.
- `lib/roles.ts` — роли и матрица прав.
- `lib/passwords.ts` — пароли (scrypt).
- `lib/stages.ts` — условия перехода между этапами.
- `lib/tasks/` — шаблон v3, генерация плана, триггеры.
- `lib/notifications/` — уведомления.
- `lib/actions/` — действия (server actions), `lib/queries/` — выборки.
- `app/` — страницы, `components/` — интерфейс, `tests/` — тесты.
