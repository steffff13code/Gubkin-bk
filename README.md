# Бизнес-клуб Губкина — платформа организаторов

Рабочее место организатора мероприятий: поток мероприятий, карточка с
задачами по регламенту, уведомления в Телеграм, регламенты, идеи.
Контекст и модель данных — см. исходное ТЗ; решения по неоднозначностям
зафиксированы в [`DECISIONS.md`](./DECISIONS.md).

Стек: Next.js (App Router) + TypeScript + Tailwind, PostgreSQL + Prisma,
grammY-бот для уведомлений, node-cron.

## Как входить

Вход — не через Telegram, а по человеку и паролю роли:

1. На странице «Войти» человек выбирает себя в списке (список сгруппирован
   по отделам).
2. Вводит пароль **своей роли**. У каждой роли один общий пароль:

| Роль | Пароль по умолчанию | Что может |
|---|---|---|
| Участник | `member-gubkin` | закрывать свои задачи, брать задачи на себя, прикреплять ссылки, писать идеи и голосовать |
| Руководитель | `lead-gubkin` | всё, что участник, плюс создавать мероприятия (в т.ч. из идей), ставить даты, назначать задачи, вести свои мероприятия, править регламенты |
| Администратор | `admin-gubkin` | всё, плюс согласование, любые мероприятия, люди и роли, шаблоны задач, пароли, удаление |

Без входа можно смотреть Поток, регламенты и отправить анонимную идею.

После входа человек попадает в **«Мой день»** — личный кабинет: свои задачи
по срокам (просрочено / сегодня / неделя / позже / ждут события), регламент
своего отдела и общие регламенты, мероприятия, где он лид или исполнитель.
Руководителю и заместителю отдела дополнительно видны задачи отдела без
исполнителя (кнопка «Взять на себя») и загрузка команды; администратору —
что ждёт согласования, застрявшие мероприятия и задачи без исполнителя.

## Запуск в работу (чек-лист администратора)

1. Войдите как «Администратор» с паролем `admin-gubkin` (этот
   пользователь создаётся при первом запуске и не является демо).
2. **Настройки → Люди**: переименуйте «Администратор» в себя, добавьте
   участников клуба — имя, роль, отдел и должность в отделе
   (руководитель / заместитель / участник). От должности зависит, кому
   автоматически уходят задачи отдела при разворачивании плана.
3. **Настройки → Доступ и запуск**: смените пароли всех трёх ролей и
   раздайте их людям. Пока пароль по умолчанию, у администратора в шапке
   висит красное предупреждение.
4. Там же удалите **демо-данные** (тестовые люди по отделам, пример
   мероприятия, три идеи с меткой «пример»). Удалять нужно под своим, не
   демо-аккаунтом.
5. Каждый участник подключает уведомления сам: **Профиль → Подключить
   Telegram** — открывается бот с персональной ссылкой, после «Start»
   дайджест и напоминания приходят ему в личку.

Стартовые пароли можно задать и переменными `MEMBER_PASSWORD`,
`LEAD_PASSWORD`, `ADMIN_PASSWORD` — они используются только при первом
запуске, дальше пароли хранятся в базе (scrypt-хэш) и меняются в
настройках.

## Самый быстрый способ посмотреть (Render, без установки)

1. Зайдите на https://render.com и нажмите «Get Started» → войдите через GitHub.
2. В панели: **New +** → **Blueprint** → подключите репозиторий
   `steffff13code/Gubkin-bk` → в поле Branch выберите
   `claude/business-club-platform-y0k1oq` → **Apply**.
3. Render создаст бесплатную PostgreSQL и веб-сервис по `render.yaml`,
   соберёт Docker-образ (5–10 минут), применит миграции и сид.
4. Откройте адрес вида `https://gubkin-bc.onrender.com` из панели.

Чтобы подтянуть новые изменения ветки: сервис `gubkin-bc` → **Manual
Deploy** → **Deploy latest commit**.

Бесплатный тариф засыпает после 15 минут простоя — первое открытие
может занять до минуты (в это время сверху бежит золотая полоса загрузки).
Для постоянной работы клуба возьмите платный инстанс (Starter) —
он не засыпает. Чтобы включить уведомления, заведите бота (см. ниже) и
заполните `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` в Environment
сервиса на Render.

## Быстрый старт (Docker)

```bash
cp .env.example .env
# заполните SESSION_SECRET; для уведомлений — TELEGRAM_BOT_TOKEN, TELEGRAM_BOT_USERNAME

docker compose up --build
```

Приложение поднимется на `http://localhost:3000`, миграции и сид
выполняются автоматически при старте контейнера `web`.

## Локальный запуск без Docker

Нужен Node.js 20+ и PostgreSQL 16 (локально или в контейнере).

```bash
npm install
cp .env.example .env
# укажите DATABASE_URL на вашу Postgres, остальные переменные — см. ниже

npm run db:migrate   # применяет миграции, спросит имя при первом запуске
npm run db:seed      # отделы, шаблон задач «Лекция», пароли ролей, регламенты, админ; демо-данные — только при первом запуске
npm run dev
```

Приложение — на `http://localhost:3000`. Бот и cron-джоба поднимаются
и в `next dev`, и в `npm start`, если `ENABLE_SCHEDULER=true` (см.
«Фоновые задачи» ниже); для проверки уведомлений без ожидания часа
есть ручной запуск `/api/cron/run`.

Сид можно запускать повторно: он не пересоздаёт удалённые демо-данные и
не трогает пароли, уже изменённые в настройках.

## Переменные окружения

См. `.env.example`. Коротко:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | строка подключения к Postgres |
| `SESSION_SECRET` | секрет для подписи cookie сессии и ссылок подключения бота (любая случайная строка) |
| `MEMBER_PASSWORD`, `LEAD_PASSWORD`, `ADMIN_PASSWORD` | необязательные стартовые пароли ролей (только первый запуск) |
| `TELEGRAM_BOT_TOKEN` | токен бота от @BotFather (для уведомлений) |
| `TELEGRAM_BOT_USERNAME` | имя бота без `@`, для кнопки «Подключить Telegram» в профиле |
| `APP_URL` | публичный адрес приложения (для ссылок в уведомлениях); на Render берётся автоматически |
| `TZ` | `Europe/Moscow` — таймзона отображения и работы cron-джобы |
| `ENABLE_SCHEDULER` | `true`, чтобы поднять cron-джобу и long polling бота в этом процессе |
| `TELEGRAM_DRY_RUN` | `1` — печатать уведомления в консоль вместо отправки (для проверки) |

## Как создать Telegram-бота для уведомлений

1. В @BotFather: `/newbot`, задайте имя и username — это и есть
   `TELEGRAM_BOT_USERNAME`. Сохраните выданный токен в
   `TELEGRAM_BOT_TOKEN`. `/setdomain` не нужен — бот не участвует во входе.
2. Перезапустите приложение. В профиле у каждого появится кнопка
   «Подключить Telegram»: она открывает бота с персональной подписанной
   ссылкой (`/start <токен>`), и бот привязывает этот Telegram-аккаунт к
   человеку на платформе. Отключить можно там же.
3. `/setjoingroups` и `/setprivacy` можно оставить по умолчанию — боту
   нужны только личные сообщения.

## Как поменять сроки в шаблоне задач

Основной способ — интерфейс: `/settings` → вкладка «Шаблоны задач»
(только для ADMIN). Там можно поменять смещение в днях, отдел,
обязательность, триггер, правило автозакрытия (например, «закрыть,
когда прикреплён фотоотчёт») и удалить/добавить задачи для любого типа
мероприятия — это применится ко всем мероприятиям, для которых план
ещё не был развёрнут (существующие развёрнутые планы не пересчитываются
задним числом).

Регламент «Лекция с гостем» изначально засеян из
`lib/tasks/lecture-template.ts` (раздел 7 исходного ТЗ). Сид создаёт
эти строки только один раз (`prisma/seed.ts` пропускает шаг, если для
`LECTURE` уже есть шаблон в базе) — поэтому правка файла и повторный
`npm run db:seed` ничего не изменят в уже существующей базе. Меняйте
сроки через `/settings`, либо для новой базы — правьте файл до первого
запуска сида.

## Фоновые задачи (бот и уведомления)

`instrumentation.ts` при старте серверного процесса (только в Node.js
рантайме и только если `ENABLE_SCHEDULER=true`) поднимает:

- long polling grammY-бота (`lib/bot.ts`) — обрабатывает `/start`;
- часовую cron-джобу (`lib/scheduler.ts`, `node-cron`, таймзона
  `Europe/Moscow`) — она же в 09:00 МСК формирует ежедневный дайджест.

Держите `ENABLE_SCHEDULER=true` только на одном запущенном инстансе,
иначе уведомления продублируются (хотя `NotificationLog.dedupeKey`
частично защищает от дублей).

Ручной запуск джобы для проверки (нужны права ADMIN, сессия — через
залогиненный браузер). `?digest=1` формирует дайджест сразу, не дожидаясь
09:00:

```bash
curl -X POST -H "Cookie: gbc_session=<значение cookie>" "http://localhost:3000/api/cron/run?digest=1"
```

В ответе — каждая попытка отправки: кому, что и с каким результатом —
`sent`, `duplicate` (уже отправляли), `capped` (лимит 3 сообщения в день,
уйдёт в дайджест), `no_bot` (человек не подключил Telegram в профиле), `failed`
(Telegram недоступен). В журнал `NotificationLog` пишется только реально
доставленное, так что сообщения не теряются, пока бот не подключён.

Проверить правила без бота: `TELEGRAM_DRY_RUN=1` — сообщения печатаются
в консоль сервера вместо отправки. На боевом сервере не включайте.

## Тесты

```bash
npm run test
```

25 юнит-тестов: генерация плана задач по шаблону (`lib/tasks/generate.ts`),
условия входа в стадии (`lib/stages.ts`), текст дайджеста и московские
календарные сутки (`tests/notifications.test.ts`). База данных не нужна.

## Структура

- `prisma/schema.prisma` — модель данных.
- `prisma/seed.ts`, `prisma/regulations-seed-data.ts` — сид.
- `lib/tasks/` — генерация плана задач по шаблону и триггеры.
- `lib/stages.ts` — условия входа в стадии мероприятия.
- `lib/notifications/` — правила автоматизации и уведомлений (раздел 8 ТЗ).
- `lib/actions/` — server actions (мутации).
- `lib/queries/` — серверные выборки для страниц.
- `app/` — страницы (App Router).
- `components/` — UI-компоненты.
- `tests/` — юнит-тесты.
